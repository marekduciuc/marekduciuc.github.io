The problem

AI agents write code fast. Without a process around them, they also skip tests, drift from the requirement, push untested changes and spend tokens without limit. I wanted the speed without losing control – a process that runs the same way every time and stops when it is unsure.

What I built

A pipeline in four workflows

  • Requirements: three analysts read the issue from different angles (behaviour, risk, minimal scope); their drafts are merged into a spec with Given/When/Then acceptance criteria and a task list, then checked by testability and completeness critics.
  • Implementation: task by task, test-first. A test-writer agent writes the failing tests, an implementer makes them pass, a reviewer checks the task, and each task ends in its own commit.
  • Documentation: README, ADR and changelog written from the actual diff, then fact-checked against the code.
  • Delivery: three review lenses (spec, security, quality), two sceptics per finding, a pull request, and a CI watch with a test-first fix loop. Merge only with explicit approval.

Guardrails, not good intentions

  • Human approval gates: a person approves the spec before any code is written, and the merge at the end.
  • tdd-guard hook: blocks edits to production code while a test cycle is in the red phase.
  • push-gate hook: before the AI pushes or opens a pull request in any repository, it runs the type check, lint, tests and a secret scan; a failure blocks the push.
  • Stop instead of guess: a coding step that fails is retried with the error output, then escalated to a stronger model; if that fails too, the run stops as blocked and waits for a person.

Cost control

  • Each step runs on the cheapest model that does it well – light models for mechanical steps, stronger ones for spec synthesis and the final review.
  • Every workflow has a cap on parallel agents and on agents per run.
  • Steps that need no judgement – parsing the spec, git bookkeeping, commits, CI polling – run as plain code in a small CLI instead of a reasoning agent.

Autopilot

Approved specs can be implemented in parallel: one background session per spec, each in its own git worktree, each ending with a code review and a pull request.

Results

  • Used to build the authentication core of a multi-tenant CRM I am developing (Spring Boot, private repository): 25 tasks and 56 acceptance criteria, merged as one pull request of 34 commits.
  • When one task got stuck on a transaction setup problem, the run stopped as blocked instead of guessing. After a manual fix it continued from the task list.
  • The next two features of the same project (27 and 24 tasks) are specified and queued for the autopilot.
  • Open source, installable as a Claude Code plugin.

What I learned

Agents for judgement, plain code for everything else. My first versions let reasoning agents do git bookkeeping and wait for CI – slow, expensive and less predictable. Moving those steps into a small CLI, writing tests in batches instead of one agent per behaviour, and capping agents per run made the pipeline cheaper and more reliable. I would start with that split next time.

Why it matters outside software

The same principles make any AI process trustworthy – in operations, customer support or purchasing:

  • Write down what "done" means before the AI starts.
  • Check the output automatically before anyone relies on it.
  • Keep a person at the decision points.
  • Let the process stop and ask, rather than guess.
  • Put limits on cost from day one.
